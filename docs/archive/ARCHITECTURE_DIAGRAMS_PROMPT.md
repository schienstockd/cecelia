# ARCHITECTURE_DIAGRAMS_PROMPT

## Goal

Generate architecture diagrams of Cecelia **from the code**, so the developer can see the implementation architecture again: what the parts are, how they depend on each other, and what the key interfaces and flows are.

The developer has lost track of the implementation. The diagrams are for a human reader. Agents do not need them.

Diagrams are **generated by scripts, not drawn by hand**, so they can be regenerated and never silently rot. This is a modern, lightweight approach: no full UML modelling.

Second goal: **framework-wide architectural coherence**. Declared architecture rules, enforced in CI and audited regularly, so the code does not wander off the intended structure (see "Architecture rules").

Output a plan first, then (after approval) the generators and diagrams. Write the plan to `ARCHITECTURE_DIAGRAMS_PLAN.md`. Do not implement until the plan is approved.

## Context

- Stack: Julia backend + Vue frontend (the "pineapple" rewrite), plus Python in places. Check the repo for what is actually current, including any legacy R/Shiny code, and state what is in or out of scope.
- Julia has no classes in the OOP sense: it has **abstract types, concrete structs and method families (multiple dispatch)**. Do not force class diagrams onto it. Decide and state how to show types and contracts, for example abstract type + its subtypes + the functions that must be implemented for it.
- Related: `CONSISTENCY_COHERENCE_AUDIT_PROMPT.md` (drift checks). Reuse its findings if present. Do not duplicate it.

## Approach

Use these, in this order of importance:

1. **C4 model (system level):** Context, Container and Component views at increasing zoom. Containers here are the runtimes: Julia backend, Python workers/tools, Vue frontend, viewer popout, storage, Claude/Kiwi integration, external services. Show protocols between them.
2. **Generated dependency graphs, per language:** module/import graphs built from the code itself, with dependency direction. Flag cycles, layering violations, god modules and dead modules. Often the most honest picture of real structure.
3. **Interface and extension-point diagrams (Mermaid):** the abstract types and function contracts a new task, population type or plot must implement. Most useful for adding functionality. Show only the main types and key members, not every field.
4. **Sequence diagrams (Mermaid):** 4-6 key flows (e.g. running a task, chain execution, gating with Claude co-driving, loading an image in the viewer). Kept as text next to the code, each step mapped to a real file and function.
5. **Data model / ER diagram:** persisted entities and files on disk, and their relationships.
6. **State diagrams** only where a real state machine exists (e.g. task lifecycle).

Drop any diagram that would be noise. Full UML class diagrams are out of scope unless a specific area truly needs one.

## Separate by language

Organise per runtime, because structure and tooling differ:

- `docs/architecture/julia/`: module graph, abstract-type hierarchies and contracts.
- `docs/architecture/python/`: module graph and key classes. Check what Python is in the repo (e.g. coastal, workers, scripts, judge tooling) and whether each part is in scope. Python-native tools (e.g. pydeps, pyreverse, or `ast`) are likely a fit.
- `docs/architecture/vue/`: component tree, stores and who reads or writes them, composables, API client boundary.
- `docs/architecture/system/`: C4 views, the **cross-language boundaries** (HTTP/WebSocket API, subprocess calls, files on disk, shared schemas), cross-cutting sequence diagrams and the ER diagram. Document each boundary contract once and link to it from both sides.

Each language gets its own generator and its own section in the plan.

## Method

1. Read the repo structure and entry points first. List modules, packages and layers with file paths.
2. Choose tooling. Prefer **text-based formats that render in GitHub and diff cleanly** (Mermaid first; D2 or PlantUML/Structurizr only if Mermaid is too limited, and say why). Evaluate existing generators per language before writing scripts from scratch:
   - Julia: introspection (`subtypes`, `fieldnames`, `methods`) or static parsing; existing packages for dependency or type graphs.
   - Python: existing import-graph and class-diagram tools.
   - Vue/JS/TS: dependency graph tools or a small AST script for imports and component usage.
3. Put generator scripts in one place (e.g. `scripts/architecture/`), with one command to regenerate everything.
4. Keep diagrams readable: aim for 15-25 nodes each. Use an explicit include list or filter and state the rule. Split by area rather than one giant diagram.
5. Verify output renders. Fix broken syntax and overlong diagrams.

## Architecture rules (framework-wide coherence)

Gap to close: there is no check or regular audit of **framework-wide coherence**. Architecture is only reviewed when building larger features, and then mostly within one area. Diagrams show what the code is; they cannot say whether it has wandered off. That needs a declared **intended architecture** to compare against.

Design:

- **Declared rules**, one small file per language (plus cross-language rules in `system/`): layers, allowed dependency directions, and boundaries between runtimes. Examples of the kind of rule: "frontend never imports backend internals", "tasks depend on core, never the reverse", "only the API layer touches storage".
- **Initial rule set proposed by Opus from the code as it is today.** Separate clearly:
  - rules the code already satisfies (safe to enforce now),
  - existing violations (list them; each needs a decision: fix, or grandfather in an explicit allowlist with a reason),
  - rules where the code shows no clear intent, which the developer must decide. Do not encode accidental structure as intent.
- **Enforced in CI as fitness functions**, so a violation fails the merge. Evaluate existing tools first: import-linter or similar for Python, dependency-cruiser or similar for Vue/JS, and a small custom test over the module graph for Julia. Allowlists shrink over time, never silently grow.
- **Regular framework-wide audit**: the weekly judge run checks soft drift the hard rules cannot express (growing god modules, inconsistent patterns for the same job across areas, boundary contracts that changed, docs or `CLAUDE.md` that no longer match the code). Use the declared rules as the reference.
- **Relation to `CONSISTENCY_COHERENCE_AUDIT_PROMPT.md`**: the declared rules are its reference. One source of truth, not two. State how the two connect and what each owns.
- **Feature work**: larger features should be checked against the rules at plan time, not only after the fact. Propose a short `CLAUDE.md` rule and a plan-time check (e.g. a reviewer step) so changes in one area are tested for effect on the whole.

In the plan: the proposed rule files, the violation list with recommended decisions, tool choices per language, CI cost, and open questions for the developer.

## Viewer boundary and view-state schema (evaluate in the plan)

Context: the viewer is a popout and is heading toward a WebGPU renderer. Game-engine thinking suggests an engine/game split: the viewer takes declarative state in and gives pixels and events out, with no knowledge of Cecelia's data model. Evaluate these against the code as it is, and report findings and recommendations. Do not build.

1. **Viewer boundary.**
   - How cleanly is the viewer separated today? List every import or call from viewer code into app stores, domain code or backend-specific types, and the reverse.
   - Propose a declared rule, e.g. "viewer imports nothing from app stores or domain code", with the current violations listed and each given a decision (fix or allowlist with reason).
   - State what the viewer's public interface is: inputs (state), outputs (events, picks, pixels), and who owns each side.

2. **One versioned view-state schema.**
   - Many existing or planned features describe "what the viewer shows": shareable views, demo replay, regenerable guide screenshots (`GUIDE_SCREENSHOTS_PROMPT`), the figure spec (`FIGURE_SPEC_PROMPT`), channel lens and populations, linked selection, vector export. Inventory what each uses today or plans to use.
   - Evaluate whether one schema can serve all of them, or where it cannot. Check the existing plans for conflicts before proposing it.
   - Treat it as a cross-runtime boundary contract: one schema, a version field, a migration path so old shared views and guide screenshots do not silently break, and a test that validates samples against it. Place it in `system/` alongside the other boundary contracts.

3. **Single owner of selection state.**
   - Find where selection and gating state lives today (plot, viewer, gating page, stores). Report duplicated or competing owners.
   - Recommend one owner with subscribers on both sides, and a rule that enforces it.

4. **Per-frame data path.**
   - Large tile and point data must not cross the Julia/Vue boundary per frame. Document how tiles, labels and track points reach the viewer today: format, caching, who decodes. Specify this as part of the boundary contract and flag anything chatty.

5. **Seams to keep, things not to build yet.**
   - Keep a thin render-backend seam. Do not build a WebGL2 fallback unless WebGPU support makes it necessary; state the trigger.
   - Do not build a render-pass graph (how a frame is composed on the GPU) until the number of passes makes plain composable layers hurt; state the trigger.
   - **Scene graph is a separate question** (the state model of what objects exist, each with transform, visibility and style, as in Imaris). Its need depends on viewer scope, so determine the scope from the code and roadmap first: mainly 2D/tiled with tracks and overlays, or true 3D volume rendering and 3D objects (cells, tracks, surfaces) that are selectable and composable in one scene. If 2D/tiled, a flat list of layers with properties is enough. If 3D, recommend a node-based model, and say that it belongs in the **view-state schema** (item 2), not in the renderer, so it stays declarative and serialisable. Size the schema to the real scope.
   - List which architecture-relevant capabilities a reference viewer such as Imaris has that this viewer lacks (3D volume rendering, composable scene objects, multi-resolution out-of-core pyramids, an extension API). Report only what affects the boundary, schema or data path, not a feature comparison.
   - A runtime debug/console panel for viewer settings is useful but not architectural; list it as optional.

Where a finding becomes a declared architecture rule, add it to the rule set in "Architecture rules". Where it affects an existing plan, name the plan and the change needed.

## Keeping them current

Keep **generation** and **interpretation** separate. Design both in the smallest form that works.

**Generation: deterministic, no LLM.**
- One regenerate command for all diagrams.
- Run it automatically in CI on merge to main (or nightly if CI cost is high). A bot opens a PR only when the output changed. Weekly generation is too laggy: diagrams would be stale most of the week.
- Fallback if CI cost or PR noise is a problem: generate inside the weekly judge run (`scripts/judge`) and commit the result. Simpler, but lags by up to a week. State the trade-off and recommend one.
- Curated parts (sequence diagrams, include lists) reference real files and functions, so a test fails when they no longer exist.
- A short rule for `CLAUDE.md` so implementing agents regenerate diagrams when they change architecture.

**Interpretation: the weekly judge run.**
- The judge reads the week's diagram diff, not the whole set, and flags: new dependency cycles, layering violations, growing god modules, new or removed boundary contracts between runtimes, and curated diagrams that have drifted from the code.
- Findings go into the judge's existing output. Check how `scripts/judge` and the consistency/coherence audit work, reuse their format and queue, and avoid adding a second place to triage. Keep it quiet when nothing meaningful changed, so it does not add to the decide-queue backlog.

In the plan, specify: the CI job, the bot PR behaviour, the judge integration point and the rule text.

## Phasing and risks

This is a lot for one pass. The plan must be phased so each phase is useful alone and can be stopped.

1. **Orientation first:** C4 system views plus a Julia module dependency graph and the interface/extension-point view. This restores the developer's mental map. Review before going further: if the developer does not read or use them, stop and say so.
2. **Rules next:** declared architecture rules and CI checks, starting with the few rules the code already satisfies.
3. **Automation last:** CI regeneration, bot PRs and judge integration, only after phases 1-2 prove useful.

Risks to address explicitly in the plan:

- **Agents editing the rules to pass CI.** Implementing agents may loosen a rule or grow an allowlist instead of fixing code. Make the rules and allowlists human-owned: protected path or CODEOWNERS, and a CI check that flags any change to them for review.
- **False positives and friction.** A noisy rule gets ignored or disabled. Start with few rules, and give each a one-line reason and a documented way to request an exception.
- **Julia tooling is immature.** Introspection needs modules to load and static parsing struggles with macros. State which approach was chosen, what it misses, and the maintenance cost of any custom tooling.
- **Hand-curated parts rot.** Sequence diagrams and include lists are the weakest link. Keep them few, and tie each to real files and functions with a test.
- **Generated is not understood.** Generated diagrams can be accurate but unreadable. Cap size and prefer a few good views over complete ones.
- **Triage overload.** The judge already has a large decide queue. Architecture findings must be few, ranked and quiet when nothing changed.

## Rules

- Read the code. Do not invent structure; every box and arrow must trace to a file.
- Fewer, readable diagrams over complete, unreadable ones.
- Keep the plan terse. Be blunt about what is messy.
