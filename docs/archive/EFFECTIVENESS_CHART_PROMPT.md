## Why

The maintainer wants to be transparent about how the repo is worked with agents and how those agents perform over time, and wants to see for himself what happens. The audience is readers of the README and the maintainer. This is not a marketing chart. An honest, readable record matters more than a flattering one.

## Starting point (a first sketch, not gospel)

You should audit and weigh all of this, and drop or replace any of it.

- **Headline chart:** failure rate per week (issues per judged session, or whatever normalized unit the data supports), a faint rolling average, markers where a CLAUDE.md rule landed, n per week shown so noisy weeks are visible, and breaks where the judge or rubric version changed.
- **Supporting chart:** open vs fix-landed vs fixed bugs per week (a burn-down).
- **Avoid:** cumulative totals, dual y-axes, causal claims from a single rule change ("dropped after", not "because of").
- **Delivery:** a static SVG generated by the weekly pass, embedded in the README. No LLM in the render step. The README text itself is never edited by automation.
- **Where it lives:** my lean was a `judge-assets` branch, force-pushed, with the README pointing at the raw URL, so `main` gets no weekly commits. Skip the push when the SVG is byte-identical. Stamp "updated <date>, n sessions" into the image.

## What I want you to decide

1. **What the data can honestly support.** Read the real run records and the rollup. How many weeks of history exist? Which metrics are stable across judge or rubric changes, and which aren't? Is a rate meaningful with this n, or should the chart show something else (counts with n, per-rule before/after, a table)? If the history is too thin for a trend line, say so and propose what to show instead.
2. **Whether two charts or one.** And whether a chart is even the right primary artifact versus a short generated "how we work with agents" page (method, what the judge measures, what it can't tell you) with the chart inside. Transparency may need method notes more than another plot.
3. **Hosting and update path.** Weigh the `judge-assets` branch against the alternatives (a docs-site file, a PR, committing to `main`). Consider caching of raw GitHub URLs, repo clutter, and what happens to the image if the branch is deleted.
4. **Rendering.** Static SVG generated deterministically in Python is the assumption. Pick the approach (matplotlib, hand-written SVG, other), keep dependencies minimal, make it readable in light and dark README themes, and give it alt text.
5. **What to publish.** Decide what is safe and useful to show. Aggregates only; no finding text, paths, uids, or session content in the image or its metadata.

## Constraints

- The judge runs with the owner's full-scope `gh` token. Any push step must go through the same allowlisted, injectable runner the issues plan describes, limited to what this task needs. Never push to `main` from automation.
- The render step is deterministic and has no LLM or untrusted text in it. If any label comes from data (rule names, for example), sanitize it for SVG/XML.
- Handle first run, empty history, and a failed push without breaking the weekly pass. A chart failure must never fail the judge.
- Don't misrepresent. If a week has few sessions, or the rubric changed, the chart must say so visibly.
