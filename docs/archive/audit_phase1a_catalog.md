# Phase 1a — Catalog of correction functions

## Scope note

**Included** — every task under `app/src/tasks/cleanupImages/` (nine files; one is a composite JSON with no `.jl`). `cleanupImages.cellposeCorrect` is retired (deleted in #610 / `CELLPOSE_V4_PLAN.md`) but included as a row because its output stores (`cpCorrected`) still live on disk and its ccid.json version key stays readable — the audit needs to see that. `importImages/saturation_run.py` is not itself a correction but writes `meta.saturation` which the denoise task's gate consumes, so it appears in the "provenance" column of denoise and in an out-of-scope note here.

**Excluded** — `editImages/register.jl` (multi-cycle stacking → new image, not a version; explicit QC-EXEMPT geometric task in the header); `editImages/{bin, copyImage, cropImage, resampleZ, tProject, zProject}` (geometric/reshape, not "corrections"); `opticalFlow/*` (trains a model rather than applying one to an image); the coastal Python engine (external dep called by `smooth`, `denoise` — its knobs live inside the tasks above).

**No spillover/overspill task exists as a separate function.** Bleedthrough is subsumed into `afCorrect` (`af_bleedthrough_alphas` in `python/cecelia/utils/correction_utils.py`, added per `AF_CORRECTION_AUDIT.md` and the `p6t4mC` case) — the task both derives α per ordered channel pair AND subtracts it before the AF ratio. See row `afCorrect` below.

## Inferred assumptions (not documented explicitly)

- **All correction tasks single-thread through one image** and use `commit_state!` (transactional) for the ccid.json update — implicit contract, never stated as an assumption in the task headers.
- **The `_spec_output_value_name(task, "…")` fallback name is what lands in ccid.json** unless the spec overrides `outputValueName` — inferred from every `_run_task` and `docs/OBJECTMODEL.md`. A user who edits `outputValueName` in a saved-params chain node can create arbitrary version keys, but none of the tasks defends against a clash with `default`.
- **Reference-channel resolution reads `default`'s `imChannelNames` in three tasks** (`driftCorrect`, `stackAlign`, `flowRegister`) via `ccid_channel_names(raw)` — this is deliberate and documented in `smooth.jl:97`, but the three tasks each carry the same pattern with no shared helper. Inferred as an implicit invariant, not a stated one.
- **`afCorrect` does NOT read `meta.saturation`** — only `denoise` does. AF's own `saturatedFrac` is derived by the run from the pixels directly. Inferred: the two saturation numbers can disagree if the AF run happens on a corrected upstream version whose saturation profile differs from `default`.
- **`driftCorrect`'s `residualRms > 2 px` threshold is `multiLag`/`chain`-specific**: `residualRms` is absent on a `sitkRigid`-only sidecar (`_drift_qc_metrics` reads `haskey(meta, "residualRms")`). Inferred: switching estimators changes which QC findings can fire, and the user isn't told.
- **`flowRegister` has no `T` axis `requires`** even though it clearly needs one — inferred from the code path and `referenceMode: previous|first`. Only spec-level gate missing among the T-only corrections.
- **`smooth`'s drift-correction prerequisite is a NAME HEURISTIC** — `occursin("rift", string(value_name)) || occursin("rift", string(filename))`. Inferred: a user who renames or ships a bespoke pipeline value_name defeats the check silently.
- **Composite ordering is JSON-only** — `afDriftCorrect` is the only composite, and its order comes from the array position in `composite: [...]`. No `before`/`after` dependency declarations exist on the task specs; composites are the only vehicle for enforced order.
- **No task declares which OTHER value_name it prefers as input** — all `valueName` params default to `"default"` regardless of which upstream corrections would be sensible. `denoise` and `smooth` have TEXT tips that say "use drift-corrected" but nothing structural.
