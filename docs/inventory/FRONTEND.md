# Frontend (`frontend/src/`)

- **A wrapping row of controls**: `.cc-row` (+ `-tight`/`-loose`) and `.cc-row-group` in `frontend/src/style.css` — the layout half of every wrapping row of items — toolbars, control bars, option rows, chip lists, legends (26 sites; 17 different gap values between them). The only rules that stay out declare a different alignment (`baseline`/`stretch`/`space-between`). Keep a toolbar's padding/border in its own scoped rule and compose (`class="ll-toolbar cc-row"`). Enforced by the `row` scenario in `utils/cssScenarios.ts`, so a new hand-rolled `flex+wrap+center+gap` fails the suite.
- **Movie output controls**: `frontend/src/components/MovieOutputControls.vue` — fps + output size, `v-model:fps` / `v-model:sizeX` / `v-model:sizeY` / `v-model:suffix` (+ `canvasX`/`canvasY` for the placeholder). Used by ViewerPanel, BatchMoviesPanel and the Animation page's side panel (`modules/animation/AnimationPanel.vue`); the three had offered DIFFERENT controls. Blank size = the napari canvas size. Parse/params logic is in `frontend/src/utils/movieSize.ts` (`parseMovieAxis`, `movieSizeParams`, `movieAxisPlaceholder` — tested); a 1-3x `res` supersample was REMOVED (it `ndi.zoom`ed the canvas screenshot: 4x the pixels, no detail). See `docs/NAPARI.md` -> *Movie output size*.
- **Recording a movie (all three surfaces)**: ONE rail — WS `movie:record` (single/animation, `handle_movie_record` -> `run_single_movie`) and `movie:batch` (`run_batch_movies`), both in `api/`. Progress comes from inside the bridge's frame loop (`_record_hooks` -> `POST /api/napari/event` -> `task:progress`) and Cancel goes `task:cancel` -> `request_batch_cancel!` -> the bridge's off-queue `record_cancel`. Don't add a blocking REST record route back — the two that existed were removed for exactly that reason. Frames are staged (`{name}.mp4.tmp.mp4`) and promoted on success, so a cancel never destroys the previous movie.
- **What a movie records, and what it puts side by side**: `frontend/src/components/MovieCompareControls.vue` (+ pure logic in `frontend/src/utils/movieCompare.ts`, tested) — TWO reorderable `ChipSelect`s, the image's VERSIONS and its SEGMENTATION masks, where the SELECTION IS THE MODE: none = the ordinary movie, one = that one, 2+ = a comparison in chip order. A movie is a **GRID**: versions across the columns, masks down the rows. Picking from BOTH lists leaves no axis to choose — the cross-product fully determines the layout (`compareShape().fixed` in TS, `_compare_grid` in Julia): 2+ of both = the cross-product, one of each = one cell. 2+ of ONE list is arranged by `compareLayout` — `row` (across), `column` (stacked) or `grid`, which WRAPS the cells into the squarest rectangle that holds them (4 → 2×2). Wrapping adds no compositor: `_wrap_grid` reshapes the single `MovieRow` into several *before* `_record_grid!` sees it (`wrapShape` mirrors it in TS), so a wrapped grid and a cross-product are the same thing downstream. Used by ViewerPanel's recorder and BatchMoviesPanel (whose single-version `<select>` it replaced). Backend: `_compare_grid` is the ONE builder; `_record_grid!` records one pass per CELL and composes NESTED — each row stitched side by side, then the strips stacked, both through the existing `movie_io.stitch_movies` (never a second compositor). Everything below the grid (the pass loop, `_grid_frame_total`, cancel, staging, the caption band) is blind to what made two cells differ and must stay that way. **The cost is multiplicative** — 2 versions × 2 masks is four renders. Config saved before versions carried a single `valueName`; read it through `versionsFromConfig` (TS) / `_config_value_names` (Julia), never directly. See `docs/NAPARI.md` → *Side-by-side comparison*, `docs/todo/MOVIE_COMPARE_PLAN.md`.
- **Segmentation masks in a movie**: `labelValueNames` on the movie config, read through `_config_label_value_names` (`api/src/napari_api.jl`) — **three-valued**: absent = leave the canvas alone, `[]` = no masks, a list = exactly those (every other registered set is hidden). It exists because `open_image` does `layers.clear()`, so a config-driven pass loses every label layer unless it asks for them back; the masks ride the OPEN (`showLabels`/`allLabels`) so the saved layer props land on them, and `_apply_label_layers!` show/hides explicitly on the passes that do NOT re-open. How much of the z stack a movie shows is `show3D` + `zSlice` on the same config, applied by the bridge's `set_z_view` (`POST /api/napari/set-z-view`) — ONE switch for image AND masks, because napari cannot project a Labels layer at all (`projection_mode` accepts only `'none'`), so "whole stack" for a mask means the volumetric render. The 3D half is the EXISTING per-set `show3D` pref the viewer's 3D button toggles — one stored value, two entry points, never a second setting. Outline width is `labelContour` on the same config (0 = filled), read through `_label_contour` and clamped at both ends; it is a napari PROPERTY set after `add_labels` (not a ctor kwarg) and lives in `_VIEW_LAYER_KEYS` so it persists and rides the per-cell view apply. **It must survive every layer REBUILD, which takes all three legs of the chain** — the bridge's `execute_command` must forward `contour` to `show_labels` (it did not: the key was on the wire from day one and the dispatcher dropped it, so every added mask was FILLED and the outline only ever appeared via the live `apply_view_state` slider — which is why it "reset" on any mask toggle, overlay restore or movie re-open, and why recordings came out filled); `labelsRequestBody`/`pushLabels` (`frontend/src/utils/napariOverlays.ts`) must put it on the request; and callers feed it from the one per-set value (`getMovieConfig(setUid).labelContour`) — the viewer's mask toggle and `useNapariAutoShow` (`_labelContour`). Pinned at both ends: `napariOverlays.test.ts` (it reaches the wire) and `test_preview_layers.py` → *the dispatcher drops no keyword the method accepts* (it reaches napari — the generic detector, so the next wire-driven parameter can't go unwired either). Skeletons use the twin key `branchValueNames` against `img.branch_labels` — same three-valued contract, separate registry, and `_apply_label_layers!` carries BOTH families in one show-labels request (two calls total, not four) so the bridge reconciles them atomically. `colourLabels` only ever RE-COLOURS a mask that is already shown — the bridge's `colour_labels` returns `{}` when no `) Labels` layer exists and never creates one.
- **Composing several movies into one frame**: `movie_io.stitch_movies` — the ONE video compositor (row/column tiles, 2 px divider, per-column caption via `title_card.caption_band`, hold-last for unequal lengths, staged-then-promoted, progress + cancel). Don't hand-roll an ffmpeg concat/hstack; and note `movie_writer` is a context manager that closes on FAILURE too (imageio's own `__exit__` closes only on a clean exit, which used to leak a staged `.tmp.mp4` on every cancelled render).
- **Movie writing (Python)**: `python/cecelia/utils/movie_io.py` — the ONE `.mp4` writer (`movie_writer`: libx264/yuv420p/quality 8/`macro_block_size=1`) plus the one size policy (`coerce_movie_size` 4096 clamp + even axes, `crop_to_even`, `size_from_xy` for the X/Y -> (h,w) flip). Used by `napari_utils._render_animation` (our own frame loop, replacing napari-animation's `animate()`) and `title_card.prepend_title_to_movie` — both halves of a file must encode the same way. Never call `imageio.get_writer` for a movie directly.
