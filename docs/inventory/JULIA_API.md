# Julia API (`api/src/`)

- **Image geometry (Julia, metadata only)**: `api/src/image_geometry.jl` — `open_level0` (level-0 array + NGFF axes, handling BOTH on-disk layouts), **`read_native` (read pixels through this, NEVER `arr[idx...]` — bioformats2raw stores are big-endian `>u2` and Zarr.jl hands back the bytes UNSWAPPED with a native eltype, so a raw `default` version silently reads as byte-swapped garbage and renders as saturated white noise; see `docs/NAPARI.md` → *Byte order*)**, `read_ngff_axes`, `axis_dims` (Zarr.jl is column-major, so C-order axis i sits at Julia dim `ndims-i+1` — never map positionally), `resolve_image_version` (a versioned `filepath` → path; `nothing` ⇒ ACTIVE), `image_geometry`, `GET /api/images/geometry`, and `GET /api/images/stores` (`store_compression` + `_path_bytes` per version/label set — what the image-metadata modal shows against each stored file; the size is a directory WALK, so it is answered on demand for one image and never folded into the `/api/images` listing). **The frame extent is per-VERSION, not per-image** — drift correction expands the canvas and a crop shrinks it — so ask this rather than storing a size on the image. Was private to the old `crop_render.jl` (`_crop_*`) until a second consumer showed none of it was crop-specific.

- **server.jl**: single `HTTP.listen` entry; `handle_stream` (WS upgrade + static serving), `handle_http` route table, `broadcast_ws` fan-out, `BroadcastLogger`, chain-event→WS bridge, `handle_ws` loop.
- **Writing a response body**: `write_http_body!` (`app/src/utils.jl`, exported) — THE way to put a materialised body on the stream, from `handle_stream`, static/asset serving and the task runner alike. Never `write(stream, body)`: no route sets `Content-Length`, so HTTP.jl frames responses CHUNKED and frames each `write` as its own chunk — a zero-length write emits the *terminating* `0\r\n\r\n` and `closewrite` emits a second, so the next response on that keep-alive connection is parsed starting at 4 stray bytes (Vite's proxy: `HPE_INVALID_CONSTANT`). One legitimately-empty response — a track-grained gating plot of an untracked segmentation — therefore failed every OTHER request sharing the connection. Enforced by the `response bodies go through write_http_body!` testset (call sites) + `an empty response body is written through write_http_body!` (the wire bytes, in the package suite).
- **sockets.jl**: `handle_message` (the one inbound-WS switch), task telemetry `ws_log`/`ws_status`/`ws_result`/`ws_progress`, `handle_task_run`/`handle_chain_run`/`handle_movie_batch`.
- **routes.jl**: project/set/image + chain-template CRUD, task-definition serving, fs browser, `api_images_tasklog` (reads the task log file), lab-log routes.
- **napari_api.jl**: the global `NapariViewer` ref + `_with_viewer` single-flight, all `/api/napari/*` handlers, `run_batch_movies`.
- **Server-side image preview render (the ONLY one — reuse it, don't hand-roll a second)**: `api/src/image_render.jl` — `composite_rgb` (multichannel → RGB: clip to contrast, colourise, additive blend; pure + unit-tested), `layer_display_specs` (the napari viewer's per-channel display settings), `percentile_spec` (auto-contrast), `CMAP_RGB` (**fallback only** — a channel's colour comes from the `colormap_lut` napari saves into the props JSON; do NOT re-derive napari's palette here, that duplication is what rendered `bop blue` as white), `render_preview_frame` (z-MIP one timepoint of one image VERSION → PNG bytes), and `cached_render!` (bounded FIFO byte cache). **Need a server-rendered thumbnail/preview? Start here.** Reads the zarr directly (`Zarr.jl`) — a sanctioned narrow carve-out for *previews only*; `zarr_utils` stays canonical for processing. Was `crop_render.jl` until an audit found nothing in it was crop-specific.
- **Crop panel routes**: `api/src/crop_api.jl` — `GET /api/crop/info` + `/api/crop/frame` (cached) and nothing else; the genuinely crop-specific part is the route names plus downscaling the reported frame size to `maxPx`. Frontend: `CropPanel.vue` (scrubbable MIP + rectangle draw + z/t + Save → `editImages.cropImage`), opened from a per-image **Crop** action in `ImageTable`'s ⋯ menu (Import page ONLY) via `CropDialog.vue` (napari-free); pure box maths in `frontend/src/utils/crop3d.ts`. Replaced the napari 3D crop. See `docs/todo/CROP_PANEL_PLAN.md`.
- **editImages.copyImage** (`app/src/tasks/editImages/copyImage.jl` + `.json`): duplicate ONE image version into a NEW image (fresh uid) in a new/existing set, dropping all derived data — a re-import shortcut. Task-rail (background + progress + universal toast). Zarr copied VERBATIM via `_copy_tree_with_progress` (Julia recursive dir copy, NOT a `zarr_utils` re-encode — preserves layout/levels/OME sidecar); `_copied_meta` carries calibration + `ori_path` + `copy_source_*`. Frontend: the **Copy** button in the Import action bar (`ImageFileActions.vue`) → `CopyDialog.vue` (version + destination-set picker; takes the whole SELECTION and dispatches one task per image). QC-exempt (duplication).
- **Image file operations (copy / move / delete)**: `frontend/src/components/ImageFileActions.vue` — the three standard file actions on the image SELECTION, mounted ONLY in `ImportModule`'s ModuleLayout `#actions` slot (no other module page can delete or re-file an image). Copy → `CopyDialog.vue`; Move → `/api/images/move` per image (manifest-only); Delete → `DeleteImagesDialog.vue`.
- **Image deletion (the ONE per-image surface)**: `frontend/src/components/DeleteImagesDialog.vue` — four radio scopes over the selection, each mapping to one route: whole images (`/api/images/delete` — a real delete: `delete_image!` `rm -r`s `0/{uid}` AND `1/{uid}`), versions + new-active (`/api/images/version/remove`), label sets (`/api/images/labels/delete`), all analysis (`/api/images/analysis/reset`). It only builds a **plan**; `ImageFileActions` executes it, so the loop + `k/N` readout + toast live in one place. Pure rules (intersection across the selection, `default`-last ordering, new-active must survive) are the tested **`frontend/src/utils/imageDelete.ts`** — don't re-derive them in a template. There are exactly **two** deletion surfaces app-wide: this modal (per-image, deliberate) and Settings → Storage (whole-project, automatic); the napari ViewerPanel label delete was removed and the `importImages.remove` task is `hidden` from module pages (still registered + a valid chain node — see `docs/MODULES.md` → *hidden*). Design + decisions: `docs/todo/IMAGE_DELETE_PLAN.md`. Move/Delete are HTTP loops and report themselves (a `k/N` readout + a completion/partial-failure toast); Copy reports through the task rail via **`taskStore.addMany(items, toastLabel)`** — the batch entry point that raises ONE "started" toast for N entries (N × `add()` = N toasts). The "existing set OR new set by name" destination + its collision check is the shared **`frontend/src/utils/setDestination.ts`** (`resolveSetDestination`/`destinationParams`, tested) — used by both Copy and Move, never re-validated inline. These were per-row actions (a ⋯ item each + a delete ✕ at the end of every row) and worked one image at a time. See `docs/UI.md` → *File operations*.
- **gating_api.jl**: population manager + gating engine routes; **owns the shared helpers** (`_gating_image`/`_resolve_vn`/`_gerr`/`_live_map`) reused by tracking/plotting/napari (include-order coupled — `gating_api.jl` first).
- **plotting_api.jl**: summary-canvas routes (thin wrappers over `plot_summary_data`).
- **tracking_api.jl**: `/api/tracking/motion-dims` preflight.
- **notebooks_api.jl**: Pluto engine lifecycle (:7660) + registry/snapshot CRUD + sysimage build. **The sysimage stamp — freshness AND which recipe built the image — has ONE implementation: `pluto/sysimage_stamp.jl`**, which this file `include`s by path (it is deliberately dependency-free so an env that can't depend on the pluto project can still load it). Don't re-derive `deps.so`/`.stamp` paths, the Manifest fingerprint, or the stamp readers here or anywhere else — that copy existed, was "kept in sync" by hand, and drifted the moment a field was added.
- **app_api.jl**: `_stop_children_for_exit`, `/api/app/shutdown|restart`, dev worktree-switch.
- **storage_api.jl**: `/api/storage/summary` (walked disk/reclaimable scan) + `/api/storage/reclaim` — thin adapters over `storage.jl`.
- **repl_api.jl / update_api.jl / setup_api.jl**: diagnostics + gated REPL; self-update; first-launch wizard.
- **task_console.jl / dev.jl**: standalone `pixi run console` WS *client*; the `pixi run dev` supervisor. (Both outside the server.)
