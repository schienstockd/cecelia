# Julia app (`app/src/`)

- **Channel name → 0-based index (Julia)**: `channel_index` / `channel_indices` / `ccid_channel_names` (`app/src/model/image.jl`) — the ONE translation from a `channelSelection` param (which stores NAMES) to the indices Python wants. Idempotent on integers; an unmatched name RAISES with the available names. Six task handlers had hand-rolled `findfirst(==(String(ch)), ch_names)` in three mutually inconsistent, silently-wrong variants (index crashed four, unmatched name dropped by five, `drift_correct` fell back to channel 0). Guarded by the `no seventh copy` detector. Python mirror: `script_utils.channel_indices`. See `docs/MODULES.md` → *`channelSelection`*.
- **Object model**: `model/image.jl` (`CciaImage` + path accessors `img_filepath`/`img_label_props_path`/`img_track_props_path`/`img_branch_props_path`/`img_branch_labels_dir`/`img_branch_labels_path`/`img_physical_sizes`), `model/set.jl` (`CciaSet`, `init_object`), `model/project.jl` (`CciaProject`, `with_transaction`).
- **"Does this image have tracks / branches" (Julia)**: `img_track_value_names(img)` / `img_branch_value_names(img)` (`app/src/model/image.jl`) — the value_names with a `{vn}__tracks.h5ad` / `{vn}__branch.h5ad` sidecar, listed from disk (one `readdir`, no HDF5 open). **Ask these, not the run log**: a migrated project carries tracks with no `tracking.*` entry, which made the guide picker declare "needs a tracked image" over an already-clustered project. Both ride the image payload (`trackValueNames`, and branch names via the pop pickers). `is_tracked(img; value_name)` is the weaker cell-table question (`track_id` in obs) and costs an HDF5 open.

- **Manual track edits**: `tracking/track_correction.jl` — the ONE place that defines what a track edit means. `apply_track_ops!`/`apply_track_op!` (the five ops in `TRACK_OP_KINDS`), `renumber_cell_ids!`, `next_track_id`, lineage reconciliation, the `corrections/{value_name}.json` journal (`load_corrections`/`append_corrections!`), and `track_correction_metrics`/`track_correction_qc_findings`. Pure — no file IO in the ops, so the task, a test and (later) the interactive staging in the API all run the same engine. **Don't hand-roll a `track_id :=` assignment anywhere else**; a join that forgets `cell_id` or a split that forgets the root convention is the bug this file exists to prevent. Task shell: `tasks/tracking/correct.jl`. Design: `docs/todo/CORRECTION_PLAN.md`, usage: `docs/TRACKING.md`.
- **Track geometry on the wire**: `track_path_dicts(df, spatial; ids)` in `tracking/track_correction.jl` — the ONE builder for per-track polylines as JSON (`{tid => {t,x,y,label}}`, time-ordered, µm). Both `/api/tracking/issues` (the candidates' geometry) and `/api/tracking/paths` (the track plot) call it, and `frontend/src/plots/trackPaths.ts` parses exactly this shape. Don't shape a third one — the two routes drifting is how a thumbnail and a plot end up disagreeing about the same track.
- **napari selection → tracks**: `GET /api/tracking/selection` (`api/src/tracking_api.jl`) resolves the transient napari cell selection (`_set_napari_selection!`, in-memory, keyed by task_dir+value_name) to the TRACKS those labels belong to, most-represented first. The bridge from "I can see that track is wrong" to a correction op; also the source of the one cell-level op (`points.remove`). Don't re-resolve labels→tracks anywhere else.

- **QC finding text**: `qc.jl` `QC_TEXT` + `qc_text(key; subs…)` — THE catalog of every user-facing QC string (`short` = the problem, `long` = the imperative action), with `{name}` placeholders filled from keywords. Emit via `qc_finding(level, code; subs…)`, which looks the text up; the four-arg `qc_finding(level, code, short, long)` remains only for custom modules. Don't inline QC prose in an analysis function again — that's what made it the least-reviewed copy in the app. **Catalog key ≠ `code`**: codes are a stored contract (banked `qc/*.json`, frontend `isMetadataCode` prefix filter), so where one code carries two wordings (`metadata.pixel_size_no_unit` for x/y vs z) or one wording serves many codes (`output.canvas_expansion` → `drift.canvas_expansion`, `cohort.outlier` → `cohort.<metric>`), pass `key =` explicitly.
- **Freeing a port from OUTSIDE the package** (the `pixi run stop*` tasks, the `api/dev.jl` supervisor): `api/portkill.jl` — `free_port(port)`, Base-only so it works with no env/manifest. SIGTERM → SIGKILL → **verifies the port is actually free**, and reports `STILL RUNNING` (exit 1) when it is not. Escalation is not optional: a Julia server whose worker threads are mid-compile ignores SIGTERM indefinitely (it prints every thread's backtrace and keeps running), which is why a single `kill` used to leave :8080 bound while `pixi run stop` printed "stopped". In-process callers use `Cecelia._kill_listeners_on_port` instead (below) — the two cannot share code across the api/app boundary, so `api/test` pins their `ss` parsers to each other. See `docs/DEV.md` → *Stopping the app*.

- **Running ONE task, from anywhere**: `app/src/runner/execute.jl` `execute_task(req::TaskRequest; on_log, on_progress, on_status, on_result)` — resolves the `fun_name`, dispatches on the task's own `scope` (a set request lands in `_execute_set_task` and its members get one joint fit), wires every callback, and guarantees a terminal `on_status` on every exit path including a `ParamValidationError` thrown before any job is queued. **All three producers go through it** — the API server (`handle_task_run` → `run_in_process`), the detached runner's task handler, and both chain node runners — so none of them can drift from the others. Everything a caller needs beyond the common case is a **field on `TaskRequest`** (`pool_name`, and `chain_run_id`/`chain_node_id` for a chain node, which ride the wire format so a runner-executed node keeps its identity): **grow the request, never fork the executor.** The chain forked it once and five bugs came out of the gap — no task log file, no task record, no run-log entry, no pool slot, no progress — each found in production, none caught by a type. Pinned by the `chain nodes run through execute_task` testset. `_run_incremental_node!` is the one runner still outside it (a lifecycle question, see `docs/TODO.md`). See `docs/SCHEDULER.md` → *Chain nodes run through `execute_task`*.

Also `ancestorsOf(nodes, edges, id)` — the transitive predecessors of a node, i.e. what has already been produced by the time it runs; it lives here because `topoOrder` builds the same adjacency and a second hand-rolled BFS is how the two drift. Mirrors Julia's `_ancestors` (`app/src/tasks/chain.jl`). Don't hand-roll a second layout or a second traversal. See `docs/UI.md` → *Chain whiteboard*.
- **The chain start dot (frontend)**: `frontend/src/utils/startDot.ts` — the pure round-trip for the UML initial node: `startTargetsOf` (save), `buildStartGraph` (load), `touchesStart`/`isStartId` (exclude it from the template), and `startDotPosition(targets, layout, depth)` + `DEFAULT_START_POS` for WHERE it goes. The dot is not a template node, so `layoutDag` never sees it — placing it from a constant instead put it in the canvas corner while the tasks sat on the layout grid, which read as an unconnected start node on every authored chain. One constant, one placement rule; don't inline `{x: 20, y: 40}` again.
- **A model a chain will train, offered before it exists**: `frontend/src/utils/chainModelOptions.ts` — `withChainProducedModels(def, stems)` extends any `select` declaring `field: "models"` with what an upstream node produces, plus `modelFilename(stem)` (the stem→`.pt` rule, mirroring Julia's `flow_model_filename` in `app/src/config.jl`). A `model` select is enumerated from the global vault, which cannot see a model produced mid-run by the same chain. The server half is `_chain_produced_names` (`app/src/tasks/chain.jl`) feeding `validate_params(...; extra_options)`; **neither half works alone** — one accepts the forward reference, the other offers it. See `docs/UI.md` → *Chain whiteboard*.
- **Frame index → real time (frontend)**: `frontend/src/utils/timeAxis.ts` — `toSeconds(v, unit)` (THE time-unit conversion; `null`, never a guess, for an unrecognised unit), `frameSeconds(img)`, `frameSecondsByImage(uids, lookup)` (per-image map for a per-image-coloured plot), `sharedFrameSeconds(uids, lookup)` (the one interval covering a pooled curve). Consumers: the temporal trend plot (`plots/plot.ts` `buildTrendLine` via `BuildOpts.timeScale`, set in `canvas/SummaryPanel.vue`) and the image table's duration column (`utils/imageTable.ts`, which owned a private `toSeconds` copy before this). **Every function returns `null` rather than a fallback when the interval is unknown, and callers must then stay in frames** — an absent `timeIncrement` is "we don't know", NOT 1 s/frame, and two movies at different intervals cannot share one seconds axis. - **Chain template parse + validation**: `tasks/chain.jl` — `chain_template_from_raw(raw; name)` is the ONE parse from a JSON document to a `ChainTemplate` (`load_chain_template` reads a file through it; `api_chains_create` runs a posted document through it, so what is validated is what `run_chain` will load). `validate_chain_template(t)` is the author-time gate (unknown `fn`, dangling/self edge, cycle, unknown scope/`barrier_policy`/`resource_pool`, bad `startTargets`, out-of-spec params via `validate_params`) — throws `ChainTemplateError`. The whiteboard can't author an invalid template, but the REPL and Claude (MCP `create_chain`) can, and before this a typo surfaced mid-run *after* the user pressed Run. Don't hand-roll a second parse or a per-route check. See `docs/SCHEDULER.md` → *Who may author a template, and who may run one*.
- **Spatial gate units**: position gates (`centroid_x/_y/_z`) are stored in **µm**; the scale is the IMAGE's (`PopulationMap.physical_sizes`, stamped by `load_pop_map(img;…)`, never persisted) and is applied in ONE place — `recompute!` — so the six fetch closures can't drift. `spatial_unit` on the gating file ("px" when absent ⇒ legacy files still work); `is_spatial_axis` (excludes `centroid_t`), `has_spatial_gate` (is this strategy portable to an uncalibrated image?). NO migration: a map with no position gate adopts µm on load, so there was nothing for a converter to do. See `docs/POPULATION.md` → *Position gates are stored in µm*.
