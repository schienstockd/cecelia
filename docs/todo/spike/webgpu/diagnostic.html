WebGPU upload-path diagnostic — where is the ceiling on getting brick data resident?

Sections A–G run standalone (no server) — GPU-side upload path only. Section H measures the FULL pipeline (fetch → decode → writeBrick) end-to-end at a sweep of concurrency, and needs diagnostic_server.py running alongside on the same box: pixi run python docs/todo/spike/webgpu/diagnostic_server.py --port 7789. Open in Chrome/Chromium, click Run all, then use Copy report to paste the JSON back. Mirrors frontend/src/lib/webgpu/brickAtlasTexture.ts::writeBrick and frontend/src/utils/brickAtlas.ts::pickAtlasLayout. Read-only — never touches the actual renderer. See § "What this measures and why" at the bottom.

A · Adapter probe — real negotiated device limits

Requests powerPreference: high-performance (matches acquireGpuDevice) and negotiates maxBufferSize, maxStorageBufferBindingSize, maxTextureDimension3D/2D from adapter.limits. Flags adapter.isFallbackAdapter — a fallback software adapter produces numbers that look like a code or hardware problem but are actually a driver/Vulkan setup issue.

B · Atlas layout probe — real resident-brick capacity at multiple budgets

Runs a JS port of pickAtlasLayout (identical to frontend/src/utils/brickAtlas.ts, verbatim) against the negotiated device limits. Sweeps VRAM budgets so you can read off the current ceiling AND what a fatter budget would buy — the workstation has 32 GB VRAM, but Chromium/Dawn caps maxBufferSize at ≈4 GiB regardless of card, so any single-atlas VRAM budget over that cap wastes headroom that a multi-atlas design could reclaim. That constraint is the same on laptop and on the RTX 5000 — this section proves it.

—

C · Upload path — stage breakdown, single brick at brick-realistic shape

Mirrors writeBrick: one writeTexture call per brick, [bx, by, bz*nc] box, bytesPerRow: bx*bpv, rowsPerImage: by. Compares four paths at the same total bytes: A queue.writeTexture (the shipped path); B queue.writeBuffer → copyBufferToTexture (isolates writeBuffer staging); C createBuffer({mappedAtCreation:true}) + getMappedRange → copyBufferToTexture (the "MAP_WRITE candidate" #649 left untested); D copyBufferToTexture alone with an already-resident buffer (the GPU floor). Times each stage two ways — wall-clock (submit only) and onSubmittedWorkDone (with #649's ~100 ms floor caveat). GPU-side timestamp-query bracketing is only portable inside compute/render passes, not around writeTexture or copyBufferToTexture; encoder-level writeTimestamp is Chromium-experimental and non-portable, so we don't rely on it. The A – D difference is the honest read on writeTexture-specific overhead.

—

D · Row-vs-bytes scaling — re-verify PR #649

Sweeps nx and ny*nz independently at r16uint to check whether cost tracks row count or byte count. #649 found rows (2.96×) fit real data far better than bytes (7.41×); re-measure on this run. If the finding holds you'll see roughly constant µs/row across widths, and rising µs/row when row count grows at fixed width means the story is more complicated. Uses onSubmittedWorkDone for continuity with the prior JSON; also reports timestamp-query GPU time where available.

—

E · 256-byte pitch alignment — re-verify PR #649

Same total ny·nz at four widths — two unaligned real (441, 1104), two 256-aligned (1152, 2048). #649 saw padded vs unaligned came back near-identical (214 vs 209 ms) and refuted "writeTexture repacks unaligned rows"; re-verify that this isn't hardware-specific.

—

F · Sustained brick-realistic throughput — mean/p95/max, MB/s

Fires N back-to-back writeBrick-shape uploads into a real atlas-shaped texture_3d target (r8uint or r16uint per bpv). Reports MB/s plus per-call mean, p95, max — not just an average, because #703's finding was tail-driven (mean 5.5 ms, p99 44 ms, max 412 ms before the per-channel loop was collapsed to one call).

—

G · Same-total-bytes, many-small vs few-large

Compares the per-call overhead ceiling: same aggregate byte count, split into N bricks of size B (varied) — isolates whether "one call per brick" is already close to optimal at realistic brick sizes, or whether the codebase would benefit from coalescing (unlikely given #703's collapse already went one direction, but this closes the loop empirically at the current shape).

—

H · Live pipeline — fetch → arrayBuffer → writeBrick, concurrency sweep

Needs diagnostic_server.py running (throwaway port 7789, off all app ports). Fires N concurrent brick fetches at brick-realistic size against /synthetic-brick, then hands each payload to writeTexture exactly the way the real scheduler does. Sweeps N = 1, 4, 8, 16, 32, 64 to see whether the shipped MAX_INFLIGHT = 16 is already saturating the local pipe or leaving throughput on the table. Splits each brick's cost via X-Server-Ms (server work) vs tArrayBuffer (wire + JS decode) vs tUpload (writeBrick + submit) so a slow answer can be attributed instead of guessed at.

What this measures and why

Upload path (target). #649 measured a ~100 ms floor on onSubmittedWorkDone across 35/88/92/163 MB payloads and treated it as an artefact. This diagnostic re-runs the same test but adds an adapter-timestamp-query path (GPU-side actual duration, no timer floor) and a createBuffer({mappedAtCreation}) +copyBufferToTexture path (the "MAP_WRITE staging" candidate #649 left untested). If timestamp-query is unavailable, we still report wall-clock and onSubmittedWorkDone with the floor caveat marked.

Atlas budget at 8 GB / 32 GB. The atlas VRAM budget is the likely-binding constraint on typical bricks — not maxTextureDimension3D. But per prior memory, Chromium/Dawn caps maxBufferSize at ~4 GiB regardless of card, so any budget over that cap requires multiple atlas textures — and the codebase currently ships one atlas per image. This section runs pickAtlasLayout at 512 MB, 2 GB, 4 GB, 8 GB, 32 GB against real device limits and reports the resident-brick count at each. Read as: "how many bricks does one atlas hold at this budget, at THIS device's real limits."

Out of scope, called out. MAX_INFLIGHT/network fetch throughput needs the live API — separate diagnostic once these upload numbers are in. The two compound (network delivers the brick, upload stalls getting it resident) in ways that are easy to misattribute; keep them separate.

Notes on pickAtlasLayout while porting. Any suspicious behaviour observed while mirroring the code is dumped into the report's notes array. Nothing here modifies the renderer — this is the read-only diagnostic pass the task spec asks for.
